How to run it

git clone {{ repository_url }}.git
cd Credit-Risk
python -m venv venv && venv\Scripts\activate     # source venv/bin/activate on macOS and Linux
pip install -r requirements.txt
flask --app run db upgrade                     # create the database tables
DEMO_PASSWORD=... flask --app run seed-demo    # demo account and sample data
python run.py                                  # http://127.0.0.1:5000
python -m pytest -q                            # the tests

To reproduce the training (the dataset is not in the repository; see ml/data/README.md): python -m ml.train writes the artifacts of this site. The dimensionality analysis runs in the Colab notebook, and the monitoring with python -m ml.monitor (Phase 6).

User instructions

  1. Log in{% if demo.password %} with the demo account shown in the overview{% endif %}.
  2. Credit Evaluation → New evaluation: complete the customer and the nine fields and press Evaluate Application. The result shows the label, the risk and the model used, and it is saved in the evaluation history.
  3. Credit Evaluation → a model name opens its tab: metrics, charts, search runs and a form to try that model (that result is not saved). The Comparison tab explains how the official model was chosen.
  4. The estimate supports a decision; it must be reviewed by a person, especially for young applicants (Phase 4).

Integration with the finance module (Activity 2)

The application also manages personal finances: transactions by category and a dashboard. The button Check my credit risk of the dashboard connects it with the model by opening the credit form with two values calculated from the transactions of the user (nothing is stored):

  • Monthly income: average of the monthly income totals of the 3 most recent complete months that have income, looking back up to 12 months and never using the current month.
  • Debt-to-income ratio: the expenses of the categories marked as debt (loans, credit cards...; the names that suggest debt come premarked) averaged over the same months, divided by the monthly income.

Each value shows its origin and can be edited. Only the identifiers of the debt categories travel in the address; the values are calculated on the server from the transactions of the logged user. The user completes the rest and the official model gives the result.

Monitoring, incidents and feedback

  • Monitoring. Every prediction of a trained model is logged without the customer identity and the batch is compared with the train distribution (PSI). See Phase 6.
  • Incidents. (1) Detect: a PSI alert, an error or a report from a user. (2) Contain: if a model is not available the evaluation answers with a clear message and no result is saved; if its outputs are unreliable the official model is switched to another one by retraining or by restoring the previous artifacts. (3) Investigate with the prediction log and the data report. (4) Fix on a branch with tests and publish through a reviewed pull request. (5) Record what happened and the decision in the repository.
  • Feedback. Users and reviewers report problems or suggestions as issues in the repository, with the date, the page and what they expected. The team reviews them at the scheduled checks (Phase 6); the feedback of a domain expert is documented in Phase 4.
