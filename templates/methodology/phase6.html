Drift detection with PSI

The population stability index compares, for every feature, the share of a batch of applicants in each bin with the share of the train split in that bin: PSI = sum((actual − expected) × ln(actual / expected)). The bins are the deciles of the train split (and the categories of the employment type), stored in ml/artifacts/reference_distribution.json: only statistics, no rows.

Review, owners and retraining

  • Frequency. The PSI and the distribution of the risk labels are reviewed every month. The ROC AUC and the recall are reviewed every quarter, as soon as real outcomes are available. An extra review is done after every deployment or retraining.
  • Owners.
    • Cristhian Stiven Aza Diaz, owner of the model: performance (ROC AUC and recall) and retraining.
    • Harrison Camargo: data quality and drift (PSI).
    • Alejandro Alarcon: the application, incidents and feedback.
  • Retrain when any of these happens:
    • the PSI of any feature is above {{ psi_thresholds.alert }};
    • the ROC AUC falls more than {{ retrain_auc_drop }} below the validated value;
    • the data source, the form or the ranges of the inputs change.

Risks and quality controls

RiskControl
Data drift: applicants change.PSI per feature and label rates against the train split.
Model degradation without notice.Collect real outcomes and measure ROC AUC and recall against the success criteria.
Wrong or incompatible artifacts.The artifacts are validated by schema on every training, tests run on every pull request, and the models are pinned to the library versions they were trained with.
Age bias.Audit by age range (Phase 4), human review of rejections, and the option without age evaluated.
Privacy of the applicants.The prediction log has no name or document and is kept for a limited time (below).
Data inconsistencies.The data report documents them; new data must pass the same checks.

Update procedure

  1. Retrain with python -m ml.train on the new data (same split, cross-validation and selection rule).
  2. Check the schemas, the success criteria, overfitting and the subgroup analysis; compare with the current version.
  3. Rebuild the reference distribution (python -m ml.monitor --build-reference) and the monitoring report.
  4. Publish through a pull request with passing tests, review it and deploy. Keep the previous artifacts to be able to go back.

Retention policy of the prediction log

The log holds, for every prediction, the date, the model and version, the nine model inputs (age, income, loan amount, credit score, months employed, credit lines, loan term, debt-to-income ratio and employment type), the probability and the label. It has no name or document, but it is financial information about an applicant, so it is treated as sensitive.

  • How long. Entries are kept for at most {{ retention_days }} days (configurable with PREDICTION_LOG_RETENTION_DAYS). Longer retention needs a new decision of the team.
  • Who accesses it. Only the owner of the models and the teammates with access to the server. It is never shown in the application (only counts), it is not in the repository (the logs/ folder is ignored by git) and it is not shared outside the team.
  • How it is deleted. Run flask --app run purge-prediction-log at least every month: it deletes the entries older than the retention. To delete everything, remove the file named in PREDICTION_LOG_PATH (an empty value turns the log off). On a hosting plan with a temporary disk the log is also lost at every deployment. A request from an applicant to delete their data is handled by removing the entries of that period.
  • Reports. The monitoring report keeps only aggregated statistics, which are not personal data.
