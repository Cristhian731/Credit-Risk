Phase 1 · {{ title }}

What problem is solved, for whom, with which data and how success is measured.

Problem and context

Lenders approve or reject loan applications under uncertainty. A wrong approval (the borrower does not repay) produces a financial loss; a wrong rejection takes away a legitimate customer. Today the decision depends on the experience of the analyst and on fixed rules. A model trained on past loans can give a consistent, data-based estimate of the probability of default for every application.

Stakeholders and beneficiaries

  • Credit analysts and risk managers use the estimate to prioritize and decide applications.
  • Applicants benefit from consistent decisions and, with the finance module, from seeing their own situation.
  • The institution reduces losses from defaults and keeps good customers.
  • The project team (university course) builds, evaluates and documents the solution.

Business objectives and machine learning objectives

Business objectiveMachine learning objective
Reduce the losses caused by loans that are not repaid.Detect a good share of the applicants who default: high recall of the default class.
Treat applicants consistently.Rank applicants by risk: high ROC AUC, with a probability that maps to Approved, Medium Risk and High Risk.
Keep good customers.Keep the false alarms under control and report them (precision) so analysts can review flagged applications.
Be able to explain and audit the tool.Compare a simple model with more complex ones, document every step and keep results traceable to files.

Questions the model answers

  • What is the probability that this applicant defaults on the loan?
  • Which risk label (Approved, Medium Risk or High Risk) corresponds to that probability?
  • Which features drive the estimate, and does it treat age groups and employment types differently?

Machine learning task: binary classification. The target is Default, where 1 means that the borrower defaulted.

Data: source, variables, size and target

The data are the Loan Default Prediction Dataset published on Kaggle under a public domain license: one table with a loan identifier, the predictors and the target.

  • Sufficiency. {{ '{:,}'.format(r.before.rows) }} rows with {{ '{:,}'.format(d.defaults) }} defaults are enough to train and compare three models with a stratified 80/20 split and 5-fold cross-validation, and the classes are imbalanced ({{ pct(r.before.default_rate, 1) }} defaults), which is handled with class weights.

Feasibility

  • Technical. The data fit in memory, the three models train in minutes (see Phase 3) and the saved models are small, so the application can load them on a small server.
  • Organizational. A team of three students, one repository with a protected main branch, automatic tests on every pull request and a free hosting plan. The scope is a prototype, not a production credit system.

Limitations and risks

  • The dataset looks semi-synthetic. {% if r %} {{ '{:,}'.format(d.inconsistent_rows) }} rows ({{ '%.1f'|format(d.inconsistent_percent) }}%) have a number of months of employment that is impossible for the age of the applicant, and {% if d.no_outliers %}none of the numeric variables has outliers{% else %}the numeric variables have few outliers{% endif %}: the values are spread evenly inside narrow ranges and the features are almost independent of each other (Phase 2). {% else %} This is computed from the data report, which is not available. {% endif %} The results describe this dataset and may not transfer to the portfolio of a real lender.
  • Weak signal. The ROC AUC is moderate because only {{ d.n_model_features }} features are used and they carry little signal each.
  • Class imbalance. Defaults are a minority, so precision is low: the model flags many applications that would have been repaid.
  • Age and fairness. The age is the most important feature and the model flags young applicants far more often than older ones (Phase 4). It is a sensitive attribute and the tool must not be used for real decisions without human review.
  • Scope. The application is a prototype: the estimate supports a decision but is not a lending decision.
